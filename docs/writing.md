# 문장 규칙

**저장소의 한글 문서와 주석 전부가 대상이다.** 어떤 어휘와 구조로 쓰는지 정한다.
`docs/` 의 규칙 문서, 슬라이스 README, `content/` 의 케이스 스터디 본문,
그리고 **한글로 쓴 코드 주석**이 대상에 포함된다.
주석도 사람이 읽는 글이라 문서와 같은 규칙을 따른다. 식별자·문자열·커밋 메시지는 대상이 아니다.

무엇을 담을지는 주제마다 다른 문서가 정한다.
이 문서는 **담은 것을 어떤 어휘와 구조로 쓰는지**만 정한다.

**조항 30개는 Kozipsa(`admin-next/docs/writing.md`)에서 그대로 가져왔다.**(2026-11-11 사용자 결정)
아래 원칙 절과 예시에 나오는 `apps/` · `packages/` 경로는 그 저장소의 것이다.
조항이 어디서 나왔는지 보여 주는 이력이라 고치지 않는다.
이 저장소에서 새로 만든 조항은 31번부터 붙인다.

Markdown 표기를 정하는 조항이라 주석에는 적용하지 않는다.
**12번은 주석 중 JSDoc 에만 적용한다.** 편집기가 그 블록만 Markdown 으로 렌더한다.
23~29번은 주석 전용이라 문서에는 적용하지 않는다.

1. **사실이 3개 이상 이어지면 불릿으로 끊는다.**
   - 번호 목록에서는 굵은 제목만 남기고 부연을 하위 불릿으로 내린다.
     부연이 한 문장이어도 내린다.(`**본문은 text-sm 이다.** 기본값이라 대개 적지 않는다.` 의 뒷문장)
   - 불릿 하나는 줄을 바꾸지 않고 이어 쓴다. 줄바꿈으로 나누면 불릿 하나가 몇 줄인지 눈으로 세야 한다.
   - 짧은 절의 산문 2줄은 그대로 둔다.(`배경과 텍스트`, `브랜드` 절이 그렇다.)
2. **문장은 결론까지 닫고, 설득하는 말은 넣지 않는다.**
   - `근거가 코드에 남지 않는다` 가 아니라 `남지 않기 때문에 사용하지 않는다` 다.
   - `아무도 찾아내지 못한다` 같은 과장은 뺀다. 지시와 근거만 남긴다.
   - 뜻을 더하지 않는 강조 부사와 수량 표현을 뺀다.
     (`아예 안 보여줄 것이 아니라면`→`안 보여줄 것이 아니라면`,
     `기준은 **후보 개수 하나**다`→`기준은 **목록개수**다`)
3. **평이한 어휘로 쓴다.**
   - 비유를 쓰지 않는다.(`색면`→`배경색`, `사다리`→`계층구조`, `눈금`→`범위`)
   - 의인화하지 않는다.(`조작할 수 있는 자리임을 알린다`→`조작할 수 있는 곳이다`)
   - 함축한 동사를 풀어 쓴다.(`갈리는`→`나눠지는`, `색을 박으면`→`색상을 명시하면`)
   - 동작을 비유로 부르지 않고 상태를 그대로 서술한다.
     (`그 그룹 전체를 잠근다`→`그 그룹 전체를 사용할 수 없게 한다`,
     `` `Combobox` 로 가는 것이 아니다 ``→`` `Combobox` 를 선택하지 않는다 ``)
   - 피동은 능동이나 가능형으로 바꾼다.(`앞이 읽히므로`→`앞의 요소를 읽을 수 있으므로`,
     `줄 높이는 크기에 의해 정해진다`→`줄 높이는 글자 크기가 정한다`)
   - 지시어만으로 위치를 가리키지 않는다.(`여기 넣으면`→`이곳에 추가하면`, `이 자리만 예외`→`필수 예외`)
   - 위치는 `자리` 가 아니라 `곳` 이다.
4. **용어는 실물에 있는 이름을 그대로 쓴다.**
   - 토큰 계층의 이름은 첫 글자를 올린다 — `Token` · `Primitive` · `Semantic` · `Bridge` · `Overlay`.
   - 실물에 이름이 없는 설명어는 올리지 않는다. 파일명은 실물 그대로다.(`primitive.css`)
   - 실물 이름이 있으면 별칭을 만들지 않는다.(`딤`→`Overlay`)
   - 코드에 그 철자로 등장하는 것만 영문으로 적는다. 개념을 부르는 말은 한글이다.
     (`data-theme` 을 가리키는 말은 `brand` 가 아니라 `브랜드`, `.dark` 쪽은 `모드` 다.)
   - 개발자 사이에서 통용된다는 이유만으로 영문을 남기지 않는다.
     (`Parameter`→`매개변수`, `Method`→`메서드`)(2026-08-31 에 사용자가 정했다)
   - 한글로 부르되 실물 표기가 따로 있으면 괄호로 병기한다. 한글이 앞이고 실물이 괄호 안이다.
     (`최소 폭이 있어서`→`최소 크기(width)가 있어서`, `말줄임한다`→`말줄임(...)한다`)
5. **총칭은 `색`, 개별 값이나 속성은 `색상` 이다.**
   - `색을 골라야 할 일이 생기면` 은 총칭이다.
   - `다른 색상은 값이 달라진다` 는 특정 Token 의 값을 가리킨다.
6. **숫자는 아라비아 숫자로 적고, 단위는 세는 대상에 맞춘다.**
   - `네 가지`→`4가지`, `색 다섯`→`색상 5개`.
   - 숫자와 단위는 붙여 쓴다.(`10 단계`→`10단계`)
   - 파일을 세는 곳에서는 `2가지` 가 아니라 `2곳` 이다.
7. **짧은 부연은 문장을 새로 만들지 않고 괄호로 붙인다.**
   - `오른쪽에 적힌 값은 흰 배경을 기준으로 잰 대비다. (다크 모드에서는 카드 색이 기준이 된다.)`
8. **대응 관계는 표로 옮기고, 헤더는 짧은 명사로 쓴다.**
   - 의문사를 헤더에 쓰지 않는다.(`어디`→`위치`, `언제`→`상황`, `무엇`→`내용`, `쓰는 자리`→`사용`)
9. **과거 이력은 적지 않는다.**
   - `전환 전에는 48개 파일에 섞여 있었다` 는 뺀다. 경과는 `git log` 가 갖는다.
   - 지금 값의 근거(`decorative` 는 `1.99:1`)와 남은 할 일은 남긴다.
10. **맥락이 같은데 내용만 나누고 싶으면 `<br />` 를 쓴다.**
    - 빈 줄을 넣으면 문단이 갈라져 맥락까지 끊긴다. Markdown 은 단순 개행을 무시한다.
    - 문단을 실제로 나눠야 하면 `<br />` 가 아니라 빈 줄을 쓴다.
11. **한 개념은 한 이름으로 부른다.**
    - 실물 Token 이나 클래스 이름이 있으면 그쪽을 따른다. 낱말을 고르는 근거일 뿐이고 표기는 한글이다.
      (`서체`·`글꼴`→`폰트`, 근거는 `--font-sans`)
    - prop 이름과 컴포넌트가 띄우는 문구도 같은 근거가 된다.
      (`후보`→`목록`, 근거는 `list` prop. `고르다`→`선택하다`, 근거는 `선택할 항목이 없습니다.`)
    - 이름을 바꾸면 그 문서 안의 다른 표기도 함께 바꾼다. 하나만 고치면 같은 것을 2개 이름으로 부르게 된다.
    - 순서가 없는 대상에는 서수를 붙이지 않는다.(`2번째 글꼴을 만들지 않는다`→`다른 폰트를 추가하지 않는다`)
    - 한 낱말이 뜻을 여럿 가리키면 갈래마다 다른 이름을 준다.
      (z-index 단계를 부르던 `층`→`엘리베이션 단계`. `층` 을 검증 3층과 토큰 계층도 쓰고 있었고,
      이름은 KRDS `스타일 > 엘리베이션` 의 `단계` 를 따랐다)
    - `쓴다` 는 뜻이 3가지라 갈래마다 이름이 다르다.
      도구를 쓰는 뜻은 `사용한다`, 사람이 글을 만드는 뜻은 `작성한다`,
      문서에 적는 뜻만 `쓴다` 로 남긴다.(2026-08-28 에 정했다)
12. **백틱 뒤의 조사는 띄어 쓴다.**
    - `` `@repo/auth`가 `` → `` `@repo/auth` 가 ``, `` `Set-Cookie`로 `` → `` `Set-Cookie` 로 ``.
    - 이미 저장소 문서가 이렇게 쓰고 있다.(`docs/index.md` 의 `` `packages/ui` 와 ``)
    - 주석에서는 JSDoc 에만 걸린다. 거기만 Markdown 으로 렌더되기 때문이다.(24번)
    - `{@link}` 도 같이 걸린다. 편집기가 코드 스팬으로 렌더해 백틱과 같은 모양이 된다.
      (`{@link ComplexBroadcastCreateRequest}와 동일하다` → `{@link ComplexBroadcastCreateRequest} 와 동일하다`)
      (2026-09-02 에 `apps/kozipsa/src/entities/complexBroadcast/` 를 교정하면서 사용자가 정했다)
13. **병렬 나열은 가운뎃점으로 묶는다.**
    - 쉼표와 슬래시를 바꾼다.(`auth(), signIn, signOut`→`` `auth()`·`signIn`·`signOut` ``,
      `쿠키/캐시`→`쿠키·캐시`, `로그아웃 / 세션 만료`→`로그아웃·세션 만료`)
    - 실물 표기가 둘인 것은 슬래시를 남긴다.(`AUTH_SECRET` / `NEXTAUTH_SECRET`)
14. **인용 블록은 모든 줄에 `>` 를 붙인다.**
    - 첫 줄에만 붙이면 둘째 줄부터 인용 밖으로 나온다. Markdown 이 그렇게 렌더한다.
15. **불릿도 종결어미로 닫고 마침표를 찍는다.**
    - 개조식을 서술문으로 바꾼다.(`- 최초 데이터 없을 땐 PageLoader 표시`→
      ``- 최초 데이터가 없을 때는 `PageLoader` 를 표시한다.``)
    - 표 안의 셀은 예외다. 개조식으로 둔다.
16. **조사를 생략하지 않고 보조용언을 띄어 쓴다.**
    - `탭을 벗어난 적 없어도`→`벗어난 적이 없어도`.
    - `살아있는`→`살아 있는`, `남아있는`→`남아 있는`.
17. **고정 이름을 뺀 `##` 제목에 번호를 붙인다.**
    - `원칙` · `금지사항` · `미정리 항목` · `확인방법` · `자주 하는 실수` · `이 컴포넌트를 고칠 때` 는
      어느 문서에나 같은 이름으로 있으므로 번호를 붙이지 않는다.(2026-09-02 에 사용자가 정했다) 그 사이의 본문 `##` 에만 1부터 매긴다.
      뒤의 2개는 컴포넌트 문서 3종의 고정 절이다.(`apps/ds/docs/component.md` 의 문서 규격과
      `.claude/agents/ds-structure-check.md` 8번 검사)
    - 슬라이스 리드미의 `파일` · `주의사항` · `테스트` 도 고정 이름이다.
      어느 리드미에나 같은 이름으로 있고 규격이 4토막을 고정한다.
      (`docs/index.md` 의 `슬라이스 리드미`)(2026-09-02 에 사용자가 정했다)
    - `###` 은 부모 번호를 잇는다.(`## 2. 세션 구조` 아래는 `### 2.1 쿠키 2종`)
    - 번호는 본문 안에서 절을 가리킬 때 쓴다.(`처리 규약은 3.4 참고`)
18. **번역체를 쓰지 않는다.**
    - `~에 대해서` · `~을 통해서` · `~라고 할 수 있습니다` 를 쓰지 않는다.
    - 실제로 사람이 말하듯 쓴다.(`역할에 대한 색상을 추가하는 것`→`역할을 나타내는 색상을 추가하는 것`)
    - `~를 가진다` 와 `~에 의해서` 도 같은 갈래다. 소유는 서술어로, 행위자는 주어로 옮긴다.
      2026-08-28 에 사용자가 추가했고, 그날 훑은 문서에는 이 2개가 없어 고친 예가 없다.
19. **문서와 주석은 `~한다` 로 통일한다.**
    - 개발 문서라 존댓말을 쓰지 않는다.
    - 외부 교정 지침이 `~합니다` 체를 요구해도 이 조항이 이긴다.(2026-08-31 에 사용자가 정했다)
    - 이미 지켜지고 있어 고친 예가 없다.
20. **한 문장에 하나만 담고, 같은 어미를 잇지 않는다.** - (`계층이 늘면 고를 때마다 판단이 필요하고, 기준이 문서에 없으면 사람마다 다르게 쓸 수 있어
늘리는 부분에 있어서는 신중을 기한다`→`계층이 늘면 고를 때마다 판단이 필요하다.
기준이 문서에 없으면 사람마다 다르게 쓰므로 신중하게 늘린다`)
21. **절 사이에 `---` 를 넣지 않는다.**
    - `##` 제목이 이미 경계다.
    - 이미 지켜지고 있어 고친 예가 없다.
22. **한 낱말로 굳은 합성어는 붙여 쓴다.**
    - `목록개수` · `단일선택` · `다중선택` 이 그렇다.
      (`후보 개수`→`목록개수`, `하나 고르기와 여럿 고르기`→`단일선택과 다중선택`)
    - 한 문서 안에서 붙이는 쪽과 띄우는 쪽을 섞지 않는다.(`다중 선택 모드`→`다중선택 모드`)
23. **내보내는 것에는 JSDoc 을 붙이고, 그 밖에는 `//` 를 쓴다.**
    - `export` 하는 함수·타입·상수가 JSDoc 대상이다. 타입의 필드에 무엇을 적을지는 26번이 갖는다.
      사용하는 쪽에서 이름 위에 올리면 편집기가 그대로 보여 준다.
      (`export` 함수 위의 `// 경로를 기준으로 라우트 정보를 찾는 유틸리티 함수` →
      같은 내용을 `/** */` 로)
    - 함수 몸통 안의 설명과 파일 머리말은 `//` 다.
      JSDoc 은 바로 뒤 선언에 붙으므로, 붙을 선언이 없는 곳에 쓰면 다음 줄을 문서로 오인하게 만든다.
      (`packages/util/apiLog.ts` 의 머리말이 `//` 인 이유다. `/** */` 로 바꾸면 `import` 문의 문서가 된다)
    - 주석 처리한 코드는 대상이 아니다.
24. **백틱은 JSDoc 에서만 쓴다.**
    - `//` 주석에는 쓰지 않는다. 어디서도 렌더되지 않아 백틱이 그대로 글자로 남는다.
      (``// `.toast-<종류> [data-icon] svg` 가 종류별 토큰으로 칠하며`` →
      `// .toast-<종류> [data-icon] svg 가 종류별 토큰으로 칠하며`)
    - JSDoc 은 VS Code 가 Markdown 으로 렌더해 hover 툴팁에 코드 스팬으로 보여 주므로 그대로 쓴다.
    - 살아 있는 코드에서 JSDoc 안의 백틱이 282줄, `//` 안이 14줄이다.
      (2026-08-31 에 세었고 그날 사용자가 정했다)
25. **함수 JSDoc 에는 매개변수마다 `@param` 을, 돌려주는 값이 있으면 `@returns` 를 적는다.**
    - 이름을 되풀이하지 않고 무엇을 받고 무엇을 돌려주는지 적는다.
      (`@param body` → `@param body - 크기를 잴 요청 본문`)
    - 태그 철자는 `@returns` 다. 살아 있는 코드에서 `@returns` 가 387곳, `@return` 이 33곳이다.
    - 형식이 눈에 안 들어오는 것에는 `@example` 로 입력과 출력을 나란히 붙인다.
      (`packages/util/format.ts` 의 `convertMinutesAndHourText` 가 그렇게 쓰고 있다)
    - 매개변수가 없고 이름만으로 자명한 것에는 붙이지 않는다.
      (2026-08-31 에 사용자가 정했다)
26. **타입 선언에는 무엇을 담는 묶음인지 적고, 필드 설명은 각 필드에 붙인다.**
    - 선언 위에는 산문 한두 줄만 적는다. 필드 목록을 나열하지 않는다.
      JSDoc 은 Markdown 으로 렌더돼 단순 개행이 무시되므로 목록이 한 문단으로 뭉치고,
      필드 옆 설명과 정본이 2벌이 된다.
      (`packages/util/apiLog.ts` 의 `ApiLogParams` 를 그 모양으로 고쳤다)
    - 필드 JSDoc 은 이름을 되풀이하지 않는다. 단위 · 없을 때의 동작 · 어디에 어떻게 쓰이는지를 적는다.
      (`/** HTTP 메서드 */` → `/** HTTP 메서드. 받은 문자열이 로그에 그대로 찍힌다 */`)
    - 객체 리터럴을 작성할 때 자동완성이 필드 JSDoc 을 그대로 보여 준다.
      비워 두면 그 자리가 빈칸이 되므로 필드는 모두 채운다.
      (2026-08-31 에 사용자가 정했다)
    - 줄 끝 주석이 아니라 필드 위 JSDoc 으로 적는다.
      줄 끝 주석은 자동완성 툴팁에 나오지 않아 필드를 채운 뜻이 사라진다.
      (`packages/util/apiServer.ts` 의 `abortSignal?: AbortSignal; // 요청 취소 신호` 를
      같은 내용의 필드 JSDoc 으로 옮겼다)(2026-08-31 에 사용자가 정했다)
27. **`@see` 는 `{@link}` 로 감싸고 그것이 무엇인지 덧붙인다.**
    - 감싸지 않으면 편집기가 링크를 만들지 못해 이름이 글자로만 남는다.
      살아 있는 코드에서 `@see {@link X}` 가 690곳, 맨 이름이 134곳이다.
      (`@see AdminComplexListRequest` → `@see {@link AdminComplexListRequest}`)
    - 이름만 적으면 그것이 요청인지 응답인지 반환값인지 이름을 눌러 봐야 알 수 있다.
      하이픈 뒤에 무엇인지 적는다.
      (`@see {@link AdminComplexListRequest}` → `@see {@link AdminComplexListRequest} - 요청 타입`)
    - 이미 `apps/kozipsa/src/entities/faq/services/faq.services.ts` 와
      `household/services/household.services.ts` 가 이렇게 쓰고 있다.
28. **`@param` 의 설명은 하이픈 뒤에 적는다.**
    - 살아 있는 코드에서 `@param 이름 - 설명` 이 329곳, 하이픈이 없는 쪽이 153곳이다.
      (`@param params 검색 조건` → `@param params - 검색 조건`)
    - `@returns` 에는 이름이 없으므로 하이픈을 붙이지 않는다.(`@returns 관리자 목록`)
    - 27번이 `@see` 에 같은 형식을 정했으므로 태그마다 표기가 갈리지 않는다.
29. **`@param` 과 `@returns` 에 타입을 중괄호로 적지 않는다.**
    - TypeScript 가 타입을 이미 갖고 있어 중복이고, 시그니처를 바꿀 때 함께 고치지 않으면
      주석이 사실과 어긋난다.
      (`@param {AdminRequest} params 관리자 계정 조회 요청 정보` → `@param param - 검색 조건`)
    - 살아 있는 코드에서 `@param` 은 중괄호가 없는 쪽이 488곳, 있는 쪽이 79곳이다.
      `@returns` 는 366곳과 84곳이다.
    - `apps/kozipsa/src/entities/admin/` 을 교정하면서 조항 없이 이미 이렇게 고쳤다.
      (2026-09-01 에 세었고 그날 사용자가 정했다)
30. **disabled 상태는 `비활성` 이라고 쓴다.**
    - `잠김` · `잠긴` · `잠그다` 를 쓰지 않는다. 같은 상태를 2개 이름으로 부르면 11번과 어긋난다.
      (`## 4. 잠김과 읽기 전용`→`## 4. 비활성과 읽기 전용`, `잠김 면 + 잠김색 글자 + 취소선`→`비활성 면 + 비활성 글자색 + 취소선`)
    - `잠금` 은 재입력 필드의 `LOCKED`(readOnly)에만 쓴다. `docs/form.md` 가 이 상태를 `잠금` 으로 부르고,
      거기에 `disabled` 를 쓰지 말라고 정했다.
    - `disabled` 와 `readOnly` 를 함께 가리킬 때는 두 이름을 모두 적는다.
      (`잠긴 입력에는 초기화 버튼을 두지 않는다`→`disabled 나 readOnly 인 입력에는 초기화 버튼을 두지 않는다`)
    - 선택되지 않은 것은 `비활성` 이라고 부르지 않는다.(`비활성 탭의 이름`→`선택되지 않은 탭의 이름`)
    - 상태를 묶어 부를 때는 무엇의 상태인지 붙인다.
      컴포넌트를 조작해서 생긴 것(선택 · hover · 비활성)은 `인터랙션 상태`,
      대상이 가진 값이나 업무 단계(사용 · 진행중 · 반려)는 `데이터 상태` 다.
      Token 이름에서 온 `상태 레이어`(`--state-*`)와 절 이름 `상태·피드백` 은 그대로 둔다.(2026-10-07 에 사용자가 정했다)
    - 코드 식별자(`disabled`, `disabled-surface`)는 그대로 둔다.(2026-10-07 에 사용자가 정했다)

## 조항을 늘릴 때

**교정하다 발견한 규칙은 바로 이 문서에 넣는다.**
메모리에 두지 않는다.
다음 세션에서는 그 규칙이 있었다는 사실조차 남지 않기 때문이다.(루트 `CLAUDE.md` `# 규칙`)

조항 하나는 3요소로 쓴다.

| 요소 | 내용                                                       |
| ---- | ---------------------------------------------------------- |
| 규칙 | 굵은 한 줄. 지시형으로 끝낸다                              |
| 예시 | 실제로 고친 `이전`→`이후` 1개 이상                         |
| 근거 | 실제 코드 경로, 기존 문서 조항, 사용자가 정한 시점 중 하나 |

**이미 지켜지고 있어 고친 예가 없으면 그 사실을 적는다.**
예시를 비워 두면 조항이 무엇을 막으려는 것인지 알 수 없고,
없는 예시를 지어내면 근거가 거짓이 된다. 19 · 21번이 그렇다.

조항 번호는 고정한다.
새 조항은 뒤에 붙이고, 겹치는 조항이 생기면 묶어서 번호를 다시 매긴다.
`/doc-write` 와 `/comment-write` 는 조항 개수를 모르므로 조항이 늘어도 스킬을 고치지 않는다.

## 금지사항

| 금지                              | 대신                          | 근거                                                                  |
| --------------------------------- | ----------------------------- | --------------------------------------------------------------------- |
| 규칙 조항을 스킬 파일에 옮겨 적기 | 이 문서를 읽게 하기           | 같은 내용이 2곳에 생긴다. 문서를 고칠 때 스킬에는 옛 내용이 남는다    |
| 규칙을 `CLAUDE.md` 에 넣기        | 스킬 호출 때만 이 문서를 읽기 | 모든 세션이 매번 읽게 된다. 코드만 고치는 세션에는 필요 없는 내용이다 |
| 예시 없이 조항만 적기             | 고친 `이전`→`이후` 를 붙이기  | 조항 문구가 어떤 동작을 막으려는 것인지 알 수 없다                    |
| 조항을 요약해서 쓰기              | 조항 전문을 읽기              | 요약에 남은 몇 개만 지켜지고 나머지는 잊힌다                          |
| 인용·코드 블록에 규칙 적용하기    | 그대로 두기                   | 인용은 원문이고, 식별자와 문자열은 프로젝트 관례를 따른다             |
