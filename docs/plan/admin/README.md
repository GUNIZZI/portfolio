# 프로젝트 관리 (`/admin/projects`) — 기획

포트폴리오에 싣는 프로젝트를 등록하고, 고치고, 공개 여부 · 홈 노출 · 순서를 정하는 관리 화면이다.
공개 화면과 따로 두고 관리자 1명만 들어온다.

이 문서는 **신규 화면 기획**이다.(`../README.md` 3.1)
요구사항에 없어 기획안으로 채웠던 항목은 사용자가 모두 채택했다.(요구사항 23) 요구사항 25 · 26 에 딸려 채운 기획안도 모두 채택했다.(요구사항 27) 그 뒤 요구사항 29 · 31 에 딸려 채운 기획안에는 `제안` 을 붙였다. 정하지 않은 것은 [검토 필요 사항](#검토-필요-사항)에 남아 있다.
로그인과 관리 화면의 머리(메뉴)는 구현했다(2026-11-17). 로그인의 기획은 [login/](./login/README.md) 에 따로 있다. 프로젝트의 목록 · 등록 · 수정 · 삭제 · 공개 · 홈 노출 · 순서도 구현했다(2026-11-19). 요구사항 29 ~ 32(상세 항목 입력 · 버튼으로만 순서 변경 · 썸네일 줄이기 · 본문 에디터와 템플릿)도 구현했다(2026-11-19).

## 요구사항

사용자가 정한 요구사항이다. 날짜를 적지 않은 것은 2026-11-12 에 정했다.

1. **포트폴리오 등록 관리를 위한 관리 기능을 추가한다.**
2. **관리 대상은 포트폴리오(프로젝트)만이다.** 기술 · 소개는 다루지 않는다. → 바꿨다. 요구사항 16
3. **배포는 Vercel 에 하고, 나중에 한다.**
4. **저장소는 Firebase 가 아니어도 된다. 저렴하게 쓸 수 있는 곳을 고른다.**
5. **프로젝트 상세 항목(역할 · 기간 · 기술 · 링크 · 본문)은 나중에 정한다. 지금은 관리 방식만 기획한다.** → 바꿨다. 요구사항 29
6. **관리 기획은 공개 화면 기획과 따로 둔다.**
7. **아래 5가지는 기획안대로 간다.**
    - entity 에 `actions` 계층을 둔다.
    - 기획과 커밋의 구역에 `관리` 를 더한다.
    - 입력 · 스위치 · 다이얼로그 · 토스트는 지금의 토큰으로 `src/shared/ui/` 에 새로 만든다.
    - `/project-add` 스킬은 지운다.
    - 프로젝트 본문은 MDX 가 아니라 Markdown 으로 쓴다. → 바꿨다. 요구사항 12
8. **저장소는 Firestore + Firebase Auth + Vercel Blob 조합으로 한다. 기능 개발과 연동은 당장 하지 않고 적어만 둔다.**
9. **로그인은 Firebase Auth 를 쓰고, 관리자 계정은 Firebase Auth 에 등록해서 쓴다.** → 로그인 기획으로 옮겼다. 요구사항 20
10. **프로젝트는 `slug` 가 아니라 `id` 로 구분한다. `id` 는 저장소가 발급한다.**
11. **공개 프로젝트가 없으면 홈의 프로젝트 섹션을 감추지 않고, 프로젝트가 없다고 보여 준다.**
12. **프로젝트 본문은 Tiptap 에디터로 쓴다.** Kozipsa 가 쓰는 에디터다. Markdown 은 쓰지 않는다. 본문은 에디터가 내는 HTML 로 저장한다.(2026-11-16)
13. **로그인은 이메일과 비밀번호로 한다. 세션은 2시간 동안 유지한다.**(2026-11-17) → 로그인 기획으로 옮겼다. 요구사항 20
14. **비밀번호는 서버에서 확인한다. 관리자는 `ADMIN_UID` 환경 변수와 UID 가 같은 계정 1개다.**(2026-11-17) → 로그인 기획으로 옮겼다. 요구사항 20
15. **관리 기획에서는 「작업」 을 「프로젝트」 라고 부른다.**(2026-11-17)
16. **소개 데이터도 저장소에서 관리한다.** 소개 페이지의 경력 · 인트로 · 일하는 방식 · 기술 묶음과 홈의 소개 문단 · 숫자다. 홈의 기술 아이콘은 다루지 않는다.(2026-11-17)
17. **프로젝트를 먼저 저장소로 옮기고, 소개는 그다음에 옮긴다.**(2026-11-17) → 바꿨다. 요구사항 24
18. **관리 화면의 메뉴는 프로젝트 · 소개 · 경력 3개다.**(2026-11-17) → 대시보드를 더해 4개로 바꿨다. 요구사항 22
19. **소개 · 경력 관리의 기획은 이 문서와 따로 둔다.** 소개는 `docs/plan/admin/about/`, 경력은 `docs/plan/admin/experiences/` 다.(2026-11-17)
20. **로그인의 기획은 이 문서와 따로 `docs/plan/admin/login/` 에 둔다.** `/admin` 과 `/admin/login` 이 로그인이다.(2026-11-17)
21. **프로젝트 목록의 주소는 `/admin/projects` 다.**(2026-11-17)
22. **관리 화면의 메뉴에 대시보드를 더한다. 로그인한 뒤의 첫 화면은 대시보드다.** 기획은 `docs/plan/admin/dashboard/` 에 있다.(2026-11-17)
23. **이 문서에 `제안` 으로 적었던 기획안을 모두 채택한다.**(2026-11-17) 나가기 확인 창은 채택하지 않고 뺐다.
24. **소개 → 경력 → 프로젝트 → 대시보드 순으로 만든다.**(2026-11-17) 경력을 먼저 만들기 때문에, 경력의 프로젝트 연결은 프로젝트를 옮길 때 `slug` 에서 `id` 로 바꾼다.
25. **순서는 목록에서 바로 바꾼다. 행을 옮기면 곧바로 저장한다.** 순서 변경 창은 두지 않는다.(2026-11-19) 옮기는 방법은 요구사항 30 으로 바꿨다.
26. **홈에 올릴 프로젝트는 프로젝트마다 「홈 노출」 스위치로 고른다.** 「공개」 와 따로 둔다. 공개하면 작업 목록(`/work`)에 보이고, 홈 노출을 켜면 홈의 대표 작업에도 보인다. 비공개 프로젝트는 홈 노출을 켤 수 없다.(2026-11-19)
27. **요구사항 25 · 26 에 딸려 `제안` 으로 적었던 기획안을 모두 채택한다.**(2026-11-19) 검토 필요 사항 15~21 이다.
28. **목록에 홈 노출이 몇 건인지 보여 준다.**(2026-11-19)
29. **프로젝트 상세에 필요한 데이터를 모두 관리 화면에서 입력한다.** 팀 · 역할 · 맡은 범위 · 기간 · 기술 · 링크 · 본문이다. 공개 화면의 상세가 읽는 항목 전부다.([work/](../work/README.md) 「메타」 · 「데이터」)(2026-11-19)
30. **순서는 행의 위 · 아래 버튼으로만 바꾼다. 끌기는 두지 않는다. 목록은 `DataTable` 로 그린다.**(2026-11-19)
31. **썸네일의 크기는 올릴 때 알아서 줄인다. 긴 변이 최대 1000px 이다.**(2026-11-19)
32. **본문은 Tiptap 에디터로 쓰고, 등록할 때 절 제목 5개(개요 · 문제 · 해결 · 결과 · 회고)가 템플릿으로 들어가 있다.**(2026-11-19)
33. **분류는 미리 정해 둔 항목에서 Select 로 고른다.** 새로 입력하지 않는다.(2026-11-19)
34. **분류는 Admin · Dashboard · Design System · Website · Promotion · Interactive 6개다.** 경력의 프로젝트 내역을 보고 「무엇을 만들었나」 로 나눴다.(2026-11-20)
35. **본문에 이미지와 표를 넣을 수 있다.** 케이스 스터디에 화면의 스크린샷을 넣는다.(2026-11-20)

## 정책

### 접근

- `/admin` 아래의 모든 화면은 로그인한 관리자만 볼 수 있다. 서버에서 세션을 검사한다.
- 로그인하지 않고 들어오면 [로그인](./login/wireframe.html#s01)으로 보낸다.
- 로그인 수단 · 관리자 판별 · 세션 기간은 [로그인 기획](./login/README.md)이 갖는다.
- 관리 화면은 검색 색인에서 뺀다.

### 목록

- 공개 · 비공개 프로젝트를 모두 순서대로 보여 준다.
- **목록 위에 전체 · 공개 · 홈 노출 건수를 보여 준다.** `전체 4건 · 공개 3건 · 홈 노출 2건` 처럼 적는다. 스위치를 바꾸면 건수도 바로 바뀐다.(요구사항 28)
- 열은 순서 · 썸네일 · 제목 · 분류 · 공개 · 홈 노출 · 수정 일시다.
- **검색과 페이지 나누기는 두지 않는다.** 프로젝트가 많지 않다.
- 공개 스위치와 홈 노출 스위치는 목록에서 바로 바꾼다. 바꾸면 곧바로 저장한다.
- 제목을 누르면 [S-03 프로젝트 수정](./wireframe.html#s03)으로 간다.

### 순서

- **순서는 [S-01 프로젝트 목록](./wireframe.html#s01)에서 바로 바꾼다.** 순서 변경 창은 두지 않는다.(요구사항 25)
- **행의 위 · 아래 버튼으로 옮긴다. 끌기는 두지 않는다.**(요구사항 30) 첫 행의 위 버튼과 끝 행의 아래 버튼은 비활성이다.
- 목록은 경력 목록과 같은 `DataTable` 로 그린다.(요구사항 30, `src/shared/ui/dataTable/dataTable.md`)
- **옮기면 곧바로 저장한다.** 저장 버튼은 없다. 공개 스위치와 같은 방식이다.(요구사항 25)
- 저장하지 못하면 옮기기 전의 자리로 되돌리고 실패 토스트를 띄운다.
- 순서는 하나다. 작업 목록과 홈이 같은 순서를 쓴다.
- 새로 등록한 프로젝트는 맨 뒤에 놓는다.

### 홈 노출

- **홈의 대표 작업에는 홈 노출을 켠 프로젝트만 나온다.** 작업 목록(`/work`)에는 공개한 프로젝트가 모두 나온다.(요구사항 26)
- **비공개 프로젝트는 홈 노출을 켤 수 없다.** 스위치를 비활성으로 그린다.(요구사항 26)
- 새 프로젝트는 비공개로 시작하므로 홈 노출도 꺼진 채 시작한다.
- 공개를 끄면 홈 노출도 함께 끈다. 다시 공개해도 홈 노출은 꺼져 있다.
- 홈 노출의 건수는 제한하지 않는다.
- 홈에서도 [순서](#순서)대로 놓는다.

### 등록 · 수정

입력 항목이다. 규칙은 지금의 스키마를 따른다.(`src/entities/project/model/project.schemas.ts`)
목록의 카드와 상세의 머리에 나오는 기본 항목, 그리고 상세에만 나오는 상세 항목으로 나뉜다. 한 화면에서 함께 입력하고 함께 저장한다.(요구사항 29)

**기본 항목**

| 항목        | 필드        | 필수                 | 규칙                                    |
| ----------- | ----------- | -------------------- | --------------------------------------- |
| 제목        | `title`     | 필수                 | 1자 이상                                |
| 분류        | `category`  | 필수                 | 정해 둔 분류 가운데 하나                |
| 요약        | `summary`   | 필수                 | 1자 이상                                |
| 상세 주소   | `href`      | 선택                 | 비우면 프로젝트 상세를 가리킨다         |
| 썸네일      | `image`     | 선택                 | 없으면 공개 화면이 임시 이미지를 그린다 |
| 대체 텍스트 | `image.alt` | 썸네일이 있으면 필수 | 1자 이상                                |
| 공개        | `published` | —                    | 스위치                                  |
| 홈 노출     | `featured`  | —                    | 스위치. 공개가 꺼져 있으면 비활성       |

**상세 항목**(요구사항 29)

공개 화면의 상세가 메타와 본문으로 그리는 항목이다. 뜻과 보이는 순서는 [작업 기획](../work/README.md) 「메타」 에 있다. 필수 여부와 입력 방식은 기획안이다.(제안)

| 항목      | 필드     | 필수 | 입력 방식                                                                        |
| --------- | -------- | ---- | -------------------------------------------------------------------------------- |
| 팀        | `team`   | 선택 | 파트 이름과 인원을 한 줄씩 더한다. 줄마다 파트 이름 1자 이상, 인원 1 이상        |
| 역할      | `role`   | 선택 | 한 줄 글                                                                         |
| 맡은 범위 | `scope`  | 선택 | 영역 4개(기획 · 디자인 · 퍼블리싱 · 개발)마다 없음 · 전담 · 주도 · 참여를 고른다 |
| 기간      | `period` | 선택 | 시작과 끝을 `2025.06` 처럼 적는다. 「진행 중」 을 켜면 끝을 입력받지 않는다      |
| 기술      | `stack`  | 선택 | 이름을 하나씩 더한다. 끌어서 순서를 바꾼다                                       |
| 링크      | `links`  | 선택 | 이름과 주소를 한 줄씩 더한다. 줄마다 이름 1자 이상, 주소는 URL                   |
| 본문      | `body`   | 선택 | Tiptap 에디터로 쓴다. HTML 로 저장한다(요구사항 12)                              |

- 상세 항목은 모두 비워 둘 수 있다. 비운 항목은 공개 화면의 상세가 그리지 않는다.([작업 기획](../work/README.md) 「상세」)(제안)
- 맡은 범위에서 「없음」 을 고른 영역은 저장하지 않는다. 한 영역은 한 번만 저장한다.
- 기간은 시작 없이 끝만 적을 수 없다. 끝은 시작보다 앞설 수 없다.(제안)
- 기술은 소개 관리의 기술 목록과 같은 입력을 쓴다.(`src/shared/ui/chipListField/ChipListField.md`)
- 팀과 링크의 줄은 위 · 아래 버튼으로 옮기고 빼기 버튼으로 뺀다. 경력의 프로젝트 줄과 같은 방식이다.(제안, `src/features/experienceEditor/ui/ProjectRow.tsx`)
- **본문의 서식은 제목(`h2` · `h3`) · 굵게 · 취소선 · 목록 · 인용 · 코드 · 구분선 · 링크 · 이미지 · 표다.**(이미지와 표는 요구사항 35) 읽는 화면의 서식과 같은 CSS 를 써서, 쓰면서 보던 모습 그대로 읽힌다.(`src/shared/ui/tiptapViewer/TiptapViewer.md`)
- **새 프로젝트의 본문에는 절 제목 5개(개요 · 문제 · 해결 · 결과 · 회고)를 템플릿으로 넣어 둔다.**(요구사항 32) 절의 순서는 [작업 기획](../work/README.md) 「상세」 가 정했다. 수정 화면은 저장된 본문을 그대로 연다.
- 본문은 저장할 때 서버에서 정제한다. 에디터가 내는 서식의 태그만 남긴다. 읽는 화면은 정제하지 않는다.(제안, `src/shared/ui/tiptapViewer/TiptapViewer.md` 「자주 하는 실수」)
- **본문의 이미지는 썸네일과 같은 방식으로 올린다.** 형식 · 크기의 제한과 줄이는 크기가 같고, 이미지 저장소의 주소만 저장한다.(`src/features/projectEditor/model/useImageUpload.ts`, `src/entities/project/services/project.services.ts` 의 `sanitizeProjectBody`)
    - 본문에서 뺀 이미지의 파일은 저장할 때 지우고, 프로젝트를 지우면 본문 이미지의 파일도 함께 지운다.(`src/entities/project/services/project.services.ts` 의 `updateProject` · `deleteProject`)
    - 이미지를 고르면 도구 줄 아래에 대체 텍스트 입력이 나온다.(`src/shared/ui/tiptapEditor/TiptapEditor.tsx`)

**그 밖의 규칙**

- 프로젝트는 `id` 로 구분한다. `id` 는 등록할 때 저장소가 발급하고 입력받지 않는다. 등록한 뒤에는 바뀌지 않는다.(요구사항 10)
- 공개 화면의 프로젝트 상세 주소도 `id` 를 쓴다(`/work/<id>`).
- **분류는 정해 둔 항목에서 Select 로 고른다.** 새로 입력하지 않는다. 같은 분류를 다른 철자로 적지 않게 하기 위해서다.(요구사항 33)
    - **항목은 6개다. 「무엇을 만들었나」 한 가지 기준으로 나눈다.**(요구사항 34, `src/entities/project/model/project.constants.ts` 의 `PROJECT_CATEGORIES`)

        | 분류          | 담는 것                           |
        | ------------- | --------------------------------- |
        | Admin         | 관리 화면 · 백오피스              |
        | Dashboard     | 데이터를 보여 주는 대시보드       |
        | Design System | 디자인 시스템 · UI Kit            |
        | Website       | 기업 · 브랜드 · 서비스 사이트     |
        | Promotion     | 프로모션 · 마이크로사이트         |
        | Interactive   | 키오스크 · 전광판 · 체험형 콘텐츠 |

    - 경력의 프로젝트 내역에서 잡았다. 처음의 Enterprise · Web App · Landing Page 는 뺐다. Enterprise 는 고객의 성격이라 기준이 다르고, Web App 은 Admin 과 Dashboard 를 함께 덮는다.
    - 항목을 더하거나 빼려면 코드의 목록을 고친다. 관리 화면에서는 고치지 않는다.(제안)
    - 목록에서 뺀 분류가 저장된 프로젝트는 공개 화면에 그대로 나온다. 수정 화면에서는 분류를 다시 골라야 저장할 수 있다.(제안)
- **새 프로젝트는 비공개로 시작한다.** 다 쓰기 전에 공개 화면에 나오지 않게 하기 위해서다.
- **썸네일은 PNG · JPG · WebP 이고 5MB 까지다.**
- **썸네일은 올릴 때 크기를 줄인다.**(요구사항 31) 올리기 전에 브라우저에서 긴 변을 1000px 이하로 줄인다. 그보다 작은 이미지는 크기를 그대로 둔다. 형식은 WebP 로 바꾸고, 브라우저가 WebP 로 바꾸지 못하면 PNG 로 올린다.(형식은 제안)
    - 공개 화면은 저장된 이미지를 그리는 칸의 크기에 맞춰 다시 줄여서 보낸다. 지금도 그렇게 한다.(`next/image`, `src/features/featuredProjects/ui/ProjectCard.tsx`)
- 썸네일의 가로 · 세로 크기는 올릴 때 파일에서 읽어 함께 저장한다. 입력받지 않는다.
- 썸네일을 바꾸거나 지우면 이전 파일도 저장소에서 지운다.
- 필수 항목이 비었거나 규칙에 맞지 않으면 저장 버튼을 누를 수 없고, 항목마다 오류 문구를 보여 준다.
- 저장하면 목록으로 돌아가 [P-02 토스트](./wireframe.html#p02)를 띄운다.
- 저장하지 않고 나가도 묻지 않는다. 고친 내용은 남지 않는다.(2026-11-17 사용자 결정)
- 글자 수 제한은 정하지 않았다.

### 삭제

- 삭제는 [P-01 삭제 확인 창](./wireframe.html#p01)을 거친다.
- 프로젝트 문서와 썸네일 파일을 함께 지운다. 되돌릴 수 없다.

### 공개 화면 반영

- 공개 화면은 공개 프로젝트만 순서대로 그린다. 홈은 그 가운데 홈 노출을 켠 것만 그린다.(요구사항 26)
- 등록 · 수정 · 삭제 · 공개 전환 · 홈 노출 전환 · 순서 변경은 저장한 직후 공개 화면에 반영한다. 서버가 프로젝트 목록의 캐시를 지운다.
- 공개 프로젝트가 0건이면 홈의 프로젝트 섹션을 그대로 두고, 카드 대신 프로젝트가 없다는 문구를 보여 준다.(요구사항 11) **문구는 「아직 등록된 프로젝트가 없습니다」 다.**
- 공개 프로젝트는 있고 홈 노출이 0건일 때도 홈은 같은 문구를 보여 준다.

## 접근성 · 성능 고려

- 입력마다 `label` 을 잇고, 오류 문구는 `aria-describedby` 로 입력에 잇는다.
- 공개 스위치는 `role="switch"` 다. 목록에서는 어느 프로젝트의 스위치인지 이름에 넣는다.
- 다이얼로그를 열면 포커스를 창 안에 두고, 닫으면 열었던 버튼으로 돌려준다.
- 삭제 확인 창은 처음 포커스를 취소에 둔다.
- 순서는 행의 위 · 아래 버튼으로 바꾼다. 버튼의 이름에 어느 프로젝트인지 넣는다. 옮긴 뒤에도 포커스는 누른 버튼에 남긴다.
- 팀 · 링크의 줄과 맡은 범위의 선택에는 몇 번째 줄 · 어느 영역인지 이름을 붙인다.
- 본문 에디터의 서식 버튼에는 이름을 붙이고, 켜진 서식은 `aria-pressed` 로 알린다.
- 본문 에디터의 코드는 등록 · 수정 화면에서만 불러온다.
- 홈 노출 스위치도 `role="switch"` 이고 이름에 프로젝트를 넣는다. 비활성일 때는 `aria-disabled` 로 알린다.
- 토스트는 `role="status"` 로 알린다.
- 관리 화면의 코드는 공개 화면의 번들에 넣지 않는다.
