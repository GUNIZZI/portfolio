# 화면 기획

새 화면을 만들기 전에, 또는 이미 있는 화면을 정리할 때 쓰는 기획 문서를 모아 둔다.
이 폴더에는 **만들 것과 정할 것**을 적는다.

Kozipsa(`admin-next/apps/kozipsa/docs/plan/`)의 기획 체계를 가져왔다.(2026-11-12 사용자 결정)
뷰어와 생성 스크립트까지 같은 구조이고, 관리자 화면에만 있던 것(메뉴 위치 · 권한 · API)은 이 사이트에 맞게 바꿨다.

## 1. 구조

**라우트와 같은 폴더 구조로 두고, 페이지 하나가 폴더 하나다.**(Kozipsa `plan/README.md` 1번에서 가져옴)
목록과 상세처럼 한 흐름으로 읽어야 하는 페이지는 한 폴더에 둔다. Kozipsa 의 팝업 관리가 목록 · 등록 · 상세를 한 폴더에 둔 것과 같다.

| 대상                             | 문서                                |
| -------------------------------- | ----------------------------------- |
| 홈 (`/`)                         | [home/](./home/README.md)           |
| 작업 목록 · 상세 (`/work`)       | [work/](./work/README.md)           |
| 소개 (`/about`)                  | [about/](./about/README.md)         |
| 이 사이트는 이렇게 (`/colophon`) | [colophon/](./colophon/README.md)   |
| 찾을 수 없음 (404)               | [not-found/](./not-found/README.md) |

**관리 화면의 기획은 공개 화면과 따로 둔다.**(2026-11-12 사용자 결정)
구역은 `관리` 이고 `admin/` 아래에 둔다.

| 대상                 | 문서                        |
| -------------------- | --------------------------- |
| 작업 관리 (`/admin`) | [admin/](./admin/README.md) |

**와이어프레임은 [index.html](./index.html) 한 곳에서 모두 본다.**
왼쪽 메뉴에 기획 문서마다 스코프(`작업 > 목록 · 상세`)와 라우트가 있고, 누르면 오른쪽에 그 와이어프레임이 열린다.
보고 있는 화면은 주소 해시(`index.html#home/s01a`)에 남는다.
파일을 직접 열면(`file://`) 문서 단위까지만 남는다.(근거: 브라우저가 iframe 안의 주소를 읽지 못하게 막는다)

**`index.html` 은 `scripts/build-plan-index.mjs` 가 이 표와 각 폴더의 「페이지 위치」 에서 만든다. 손으로 고치지 않는다.**
`pnpm plan-index` 로 만든다.(Kozipsa 1번에서 가져옴)
스코프의 첫 항목(구역)은 커밋 영역 표기를 따른다.(근거: `docs/commit.md` 「영역」)

**`plan-index` 는 각 `wireframe.html` 의 `<!-- userflow:start -->` ~ `<!-- userflow:end -->` 구간에 `userflow.md` 본문을 넣는다.**
이 구간은 손으로 고치지 않는다.(근거: `scripts/build-plan-index.mjs` 가 실행마다 구간 전체를 바꾼다)
`userflow.md` 나 이 표를 고쳤다면 `plan-index` 를 실행한 결과까지 커밋한다.

배포는 아직 하지 않는다. Kozipsa 의 Vercel 배포 워크플로는 가져오지 않았다.(2026-11-12 플랜에서 배포를 뒤로 미뤘다)

## 2. 문서 구성

**폴더 하나에 파일 3개를 둔다.**(Kozipsa 2번에서 가져옴)

| 파일             | 내용                                                                                       |
| ---------------- | ------------------------------------------------------------------------------------------ |
| `README.md`      | 요구사항 정의서(PRD). 개요 · 용어 · 정책 · 기능 정의 · 데이터 · 검토 필요 사항             |
| `userflow.md`    | 유저 플로우. mermaid `flowchart` 로 그린다. 와이어프레임의 「유저 플로우」 구간으로 보인다 |
| `wireframe.html` | 와이어프레임과 화면 설계 명세. 브라우저로 연다                                             |

**정책은 `README.md`, 흐름은 `userflow.md`, 화면 명세는 `wireframe.html` 에 적는다.**
같은 내용을 2곳에 적지 않고 서로 링크한다.

예시는 [home/](./home/README.md) 이다.

## 3. 작성 규칙

**작성 절차는 `/plan-write` 스킬에 있다. 규칙은 이 문서에만 적고 스킬에는 순서만 적는다.**(Kozipsa 3번에서 가져옴)
**문장은 [docs/writing.md](../writing.md) 를 따른다.** 표 안의 셀은 개조식으로 둔다.

### 3.1 기획 대상 2가지

| 대상           | 근거로 삼는 것                                             | `제안` 표기                 |
| -------------- | ---------------------------------------------------------- | --------------------------- |
| 신규 화면      | 사용자가 준 요구사항, 디자인 원본(`sample/`), 앱 공통 문서 | 요구사항에 없는 것에 붙인다 |
| 이미 있는 화면 | 실제 코드(`src/app/` · `features/` · `widgets/`)           | 붙이지 않는다               |

**이미 있는 화면은 코드가 기준이다.** 코드에서 확인할 수 없는 것만 검토 필요 사항으로 보낸다.(근거: `docs/index.md` 우선순위 2)
**이미 있는 화면에 새 동작을 더하는 기획에는 2가지가 섞인다.** 코드에 있는 구조는 표시 없이 적고, 더할 동작 가운데 요구사항에 없는 것에 `제안` 을 붙인다.(2026-11-12 사용자 결정, 홈 기획)

### 3.2 `제안` 표기

**요구사항에서 정해지지 않아 기획안으로 채운 항목에는 `제안` 을 붙인다.**
그 항목마다 「검토 필요 사항」 표에 행을 하나씩 두고, 그곳에서 확정한다.(Kozipsa 3.2에서 가져옴)

`(제안)` 처럼 괄호로 붙이고, 표 헤더나 절 제목에 붙여 그 아래 전체를 묶을 수 있다.

**초안 문서는 머리말에 「초안」 이라고 적는다.** 사용자가 아직 채택하지 않은 페이지를 제안으로 채운 문서다.
채택하면 「초안」 을 지우고 검토 필요 사항을 하나씩 확정한다.(2026-11-12 사용자 결정)

### 3.3 ID

| 접두어 | 대상                          | 정의하는 곳                       |
| ------ | ----------------------------- | --------------------------------- |
| `F-`   | 기능                          | `README.md` 「기능 정의」 표      |
| `S-`   | 페이지 화면과 그 상태         | `wireframe.html` 「화면 목록」 표 |
| `P-`   | 다이얼로그 · 토스트 · 확인 창 | `wireframe.html` 「화면 목록」 표 |

**번호는 2자리로 01 부터 붙이고, 파일 3개가 같은 ID 를 쓴다.** `userflow.md` 의 노드 이름도 화면 ID 로 시작한다(`S-01 홈`).(Kozipsa 3.3에서 가져옴)

### 3.4 `README.md` (PRD)

절은 아래 순서로 둔다. Kozipsa 의 절에서 「메뉴 위치」 를 「페이지 위치」 로, 「API」 를 「데이터」 로 바꾸고 「모션」 · 「반응형」 을 더했다.

| 절                 | 담는 내용                                                   |
| ------------------ | ----------------------------------------------------------- |
| 머리말             | 무엇을 하는 페이지인지 1~2줄, 문서 상태, 파일 3개의 링크 표 |
| 요구사항           | 사용자가 정한 요구사항. 번호를 붙이고 굵게 적는다           |
| 페이지 위치        | 구역 · 페이지명 · 라우트 · 들어오는 곳                      |
| 용어               | 이 페이지에서 새로 쓰는 말                                  |
| 정책               | 구성 · 링크 · 입력 · 상태. 주제마다 `###` 로 나눈다         |
| 모션               | 요소 · 계기 · 연출 · 도구 · 동작 줄이기에서 보일 상태 표    |
| 반응형             | 화면 폭마다 달라지는 배치                                   |
| 기능 정의          | `ID · 기능 · 화면 · 설명` 4열 표                            |
| 데이터             | 어디서 읽는가(`content/` · entity · `config/`), 항목 표     |
| 접근성 · 성능 고려 | 이 페이지에서 따로 챙길 것                                  |
| 검토 필요 사항     | `No · 항목 · 기획안 · 확인 대상` 4열 표                     |

**「페이지 위치」 표는 `구역` · `페이지명` · `라우트` · `들어오는 곳` 4개 행으로 구성한다.**
`scripts/build-plan-index.mjs` 가 앞의 3개로 뷰어의 스코프를 만든다. 구역은 `메인` · `작업` · `소개` · `공통` · `관리` 중 하나다.(근거: `docs/commit.md` 「영역」)

**모션은 `docs/motion.md` 의 토큰 이름으로 적는다.** `DURATION.slow` · `EASE.enter` 처럼 쓴다. 숫자로 적지 않는다.(근거: `docs/motion.md` 원칙 2)

### 3.5 `userflow.md`

- **첫 절은 `1. 전체 흐름` 이다.** 들어오는 곳부터 페이지 사이 이동을 한 장에 그린다.
- **그다음 절은 방문자 동작마다 하나씩 둔다.** 처음 들어옴 · 작업 보기 · 연락하기처럼 나눈다.
- **도표 아래에는 도표로 나타낼 수 없는 판단을 불릿으로 적는다.**

**노드마다 종류 class 를 붙인다.**(Kozipsa 3.5에서 가져옴)

| 종류                | 모양 · class                      |
| ------------------- | --------------------------------- |
| 화면                | `["S-01 홈"]:::screen`            |
| 다이얼로그 · 토스트 | `("P-01 복사됨 토스트"):::dialog` |
| 판정                | `{"동작 줄이기인가"}:::decision`  |
| 데이터 · 외부       | `[/"메일 앱"/]:::api`             |
| 예외 상태           | `["복사 실패"]:::warn`            |
| 종료                | `(["상세로 이동"]):::done`        |
| 그 밖               | `["스크롤"]:::step`               |

- **`classDef` 는 도표에 적지 않는다.** `plan/userflow.js` 의 `CLASS_DEF` 가 도표마다 붙인다.
- **앞 단계로 돌아가는 선은 점선(`-.->`)으로 그린다.**
- **마름모에는 짧은 질문만 넣고, 조건의 상세는 도표 아래 불릿으로 보낸다.**

### 3.6 `wireframe.html`

- **스타일은 `plan/wireframe.css` 하나를 상대 경로로 불러온다.** `<style>` · `<script>` 와 그 밖의 외부 리소스는 쓰지 않는다.
  단, 유저 플로우 구간의 `plan/userflow.js` 와 그 스크립트가 불러오는 marked · mermaid 는 예외다.(Kozipsa 3.6에서 가져옴)
- **마크업은 `plan/parts.html` 의 견본을 복사해 쓴다.** 견본에 없는 부품은 `wireframe.css` 에 클래스를 추가하고 `parts.html` 에도 견본을 둔다.
- **시각 디자인을 다시 그리지 않는다.** 배치 · 순서 · 상태만 그리고, 모양은 디자인 원본(`sample/`)을 가리킨다.
  이 사이트는 완성 디자인이 있어서, 와이어프레임에 그림을 다시 그리면 같은 내용이 2곳에 생긴다.(2026-11-12 기획 체계 검토에서 제안, 사용자 컨펌 대기)
- **움직이는 요소에는 `.mo` 모션 주석을 붙인다.** 명세는 화면 아래 모션 표에 적는다.
- **변형 화면은 앞 화면과 달라지는 부분만 그린다.** 같은 칸은 「데스크톱과 같다」 처럼 적는다.
- **요소 하나를 한 줄에 쓴다.** 고칠 때 바뀌는 줄을 줄이기 위해서다.(Kozipsa 3.6에서 가져옴)
- **머리말(`.intro`)에 화면 목록 표를 둔다.** 열은 `ID · 화면 · 형태 · 라우트` 다.
- **화면은 `section.screen` 하나에 하나다.** `id` 를 붙여 화면 목록에서 링크한다.
- **번호 마커(`.m`)로 구성 요소를 가리키고, 오른쪽 `aside.notes` 에 번호별 명세를 적는다.**
- **컴포넌트 이름은 `src/shared/ui/` 와 각 `features/` 에 있는 것만 적는다.** 아직 없는 것은 `제안` 을 붙인다.

**와이어프레임은 디자인 시스템 토큰 규칙의 대상이 아니다.** 앱 코드가 아니라 기획 산출물이고, 단독으로 열리는 파일이라 `src/style/tokens` 를 불러올 수 없다.(Kozipsa 3.6에서 가져옴)

### 3.7 문서를 추가하면

**「구조」 표에 1줄을 추가하고 `pnpm plan-index` 로 뷰어를 다시 만든다.** 기획 문서의 위치는 그 표에만 적혀 있다.
