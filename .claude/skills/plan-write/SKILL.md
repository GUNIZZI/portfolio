# plan-write

Kozipsa `/plan-write` 를 가져왔다.(2026-11-12 사용자 결정)

**이 스킬에는 규칙을 적지 않는다.** 규칙은 `docs/plan/README.md` 에 있다.
파일 3종의 구성, 절 순서, ID 규칙, `제안` 표기, 와이어프레임 골격이 거기 있다.
여기가 갖는 것은 **순서**뿐이다.

## 0. 전제

- **`/plan-write` 호출로만 실행된다.** 평문 요청에는 호출해 달라고 한 줄로 안내한다.
- **페이지 하나만 쓴다.** 여러 페이지를 한 번에 받으면 하나를 고르게 한다.
- **이미 기획 폴더가 있으면 새로 쓸지 고칠지 묻는다.** 고치는 것이면 8단계로 간다.
- **코드를 고치지 않는다.** 기획 문서만 만든다.
- **커밋하지 않는다.** 끝나면 커밋 스킬을 호출하라고 안내한다.

## 1. 대상과 위치를 묻는다

**`AskUserQuestion` 으로 두 가지를 한 번에 묻는다.** 호출 인수로 이미 답이 있으면 그 항목은 건너뛴다.

| 질문      | 선택지                                                             |
| --------- | ------------------------------------------------------------------ |
| 기획 대상 | 신규 페이지(요구사항을 받는다) · 이미 있는 페이지(라우트를 받는다) |
| 저장 위치 | `docs/plan/<라우트>/` (권장) · 다른 경로                           |

## 2. 규칙과 예시를 읽는다

읽지 않고 기억에서 꺼내 쓰지 마라.

- `docs/plan/README.md` 전체
- 예시 3종 — `docs/plan/home/` 의 `README.md` · `userflow.md` · `wireframe.html`
- 부품 견본 — `docs/plan/parts.html`
- `docs/writing.md` 전체
- `docs/design.md` — 디자인 원본(`sample/`)과 토큰
- `docs/motion.md` — 모션 절을 쓸 때

## 3. 근거를 모은다

### 3.1 신규 페이지

- **요구사항을 번호 목록으로 옮겨 사용자에게 그대로 확인받을 수 있게 준비한다.** 말을 바꾸지 않는다.
- **이미 있는 페이지를 함께 본다.** 같은 부품과 표기를 쓰기 위해서다. 지금은 홈(`src/app/page.tsx`)이 기준이다.
- **쓸 수 있는 컴포넌트를 `src/shared/ui/` 와 `src/features/` 에서 확인한다.**

### 3.2 이미 있는 페이지

- `src/app/<라우트>/` 에서 페이지와 그 페이지가 부르는 `widgets/` · `features/` · `entities/` 를 읽는다.
- **화면에 보이는 문구를 코드에서 그대로 뽑는다.** 버튼 · 제목 · 링크 주소 · 대체 텍스트다. `src/config/` 와 각 `model/*.constants.ts` 도 본다.
- 디자인 원본(`sample/`)과 코드가 다르면 적어 두었다가 4단계에서 함께 낸다. 말없이 고치지 않는다.

## 4. 골격을 컨펌받는다

**세 파일을 쓰기 전에 아래를 한 번에 낸다.** 이곳이 이 스킬의 유일한 컨펌 지점이다.

```
요구사항: 1. … 2. …            (신규 페이지만)
페이지 위치: 구역 · 페이지명 · 라우트 · 들어오는 곳

기능 정의
| ID | 기능 | 화면 |

화면 목록
| ID | 화면 | 형태 | 라우트 |

유저 플로우 절: 1. 전체 흐름 → 2. … → 3. …

제안 항목
| 항목 | 기획안 | 근거 |

검토 필요 사항
| 항목 | 기획안 | 확인 대상 |
```

**`제안` 은 근거와 함께 낸다.** 이미 있는 페이지의 관례, 디자인 원본, 앱 공통 문서 조항이다.
근거를 대지 못하는 기획안은 검토 필요 사항에 "미정" 으로 남긴다.

**사용자가 「제안으로 채운 초안」 을 요청했으면 이 단계를 건너뛴다.** 초안은 채택 전의 문서라, 머리말에 「초안」 이라고 적고 모든 기획안을 `제안` 으로 둔다.(`docs/plan/README.md` 3.2)

## 5. 세 파일을 쓴다

**`README.md` → `userflow.md` → `wireframe.html` 순으로 쓴다.**
정책이 먼저 서야 흐름의 분기가 정해지고, 흐름이 서야 화면마다 그릴 상태가 정해진다.

- **ID 와 절은 4단계에서 컨펌받은 그대로 쓴다.** 쓰다가 기능이나 화면이 늘면 바로 알린다.
- **와이어프레임은 `docs/plan/parts.html` 의 견본을 복사해 쓴다.** 새 부품이 필요하면 바로 알린다.
- **새 `wireframe.html` 에는 머리말 다음에 `<!-- userflow:start -->` · `<!-- userflow:end -->` 두 줄을 두고, 머리 바로가기에 `#flow` 링크를 둔다.**

## 6. 세 파일을 대조한다

다 쓰고 나서 아래를 센다. 어긋나면 고치고, 고친 것을 보고에 적는다.

- **ID** — `README.md` 의 `F-` 와 `wireframe.html` 의 `S-` · `P-` 가 `userflow.md` 노드와 맞는가. 정의되지 않은 ID 를 가리키는 곳이 0이어야 한다.
- **링크** — 세 파일 사이의 상대 링크와 화면 목록의 `#id` 가 실제로 있는가.
- **`제안`** — `제안` 을 붙인 항목마다 검토 필요 사항에 행이 있는가.
- **컴포넌트 이름** — 와이어프레임에 적은 이름이 `src/shared/ui/` · `src/features/` 에 있거나 `제안` 이 붙어 있는가.
- **스타일** — `wireframe.html` 에 `<style>` 이 없고, `wireframe.css` 를 부르는 상대 경로가 맞는가.
- **도표** — 노드마다 종류 class 가 있고, 되돌아가는 선이 점선인가. `classDef` 를 적지 않았는가.
- **모션** — 모션 표의 값이 `docs/motion.md` 토큰 이름인가.
- **문장** — 세 파일의 산문을 `docs/writing.md` 로 대조한다. `/doc-write` 3단계와 같은 두 갈래로 보고에 붙인다.

## 7. 진입점을 잇는다

**`docs/plan/README.md` 1번 「구조」 표에 행을 추가하고 `pnpm plan-index` 로 뷰어를 다시 만든다.**
같은 실행이 `wireframe.html` 의 유저 플로우 구간도 채운다. 경고가 나오면 새 문서의 그 절이 규격대로인지 확인한다.

끝나면 세 파일 경로와 6단계 결과, 남은 검토 필요 사항 개수를 보고하고 커밋 스킬을 안내한다.

## 8. 기존 문서를 고친다

0단계에서 고치는 것으로 정했을 때만 이 단계를 탄다. 1~7단계는 건너뛰고 2단계의 규칙만 읽는다.

1. **바뀌는 정책을 받아 `README.md` 의 해당 절부터 고친다.**
2. **그 정책이 닿는 `userflow.md` 절과 `wireframe.html` 의 `section.screen` 을 목록으로 내고 컨펌받는다.**
3. **목록에 있는 부분만 Edit 한다.** 파일 전체를 다시 쓰지 않는다.
4. **6단계 대조를 거친다.** 「구조」 표나 「페이지 위치」, `userflow.md` 가 바뀌었으면 `plan-index` 도 다시 돌린다.
