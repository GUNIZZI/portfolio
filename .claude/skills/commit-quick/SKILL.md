# commit-quick

`/commit` 의 간소화 버전이다.(Kozipsa `/commit-quick` 에서 가져옴) **빠진 것은 3단계 문서 점검 하나다.**
자격증명 차단, 관심사 분할과 승인, 메시지 규칙, 검증은 `/commit` 과 같다.

## 0. 전제

- **`/commit-quick` 호출로만 실행된다.** 평문 "커밋해줘"에는 호출해 달라고 한 줄로 안내만 하고 끝낸다.
- `git commit` 은 `.claude/hooks/guard-commit.py` 가 막고 있다. 3단계의 1회용 토큰이 있을 때만 통과한다.
- `git push` 는 범위가 아니다.

## 1. 상태 파악

```bash
./.claude/skills/commit/status.sh
```

- `(변경 없음)` 이면 즉시 종료한다. `!!` 파일은 스테이징하지 않는다.
- **`=== 범위 판정 ===` 이 디자인 시스템 포함이면 여기서 멈춘다.**
  "디자인 시스템 변경이 섞여 있어 `/commit` 으로 가야 한다"고 알리고 끝낸다. 직접 넘어가지 않는다.

## 2. 관심사 분할과 승인

`/commit` 4단계와 같은 축으로 나누고, 스테이징 전에 표로 보고해 **항상 승인을 받는다.**
문서 점검을 생략하므로 분할과 메시지를 보는 곳이 여기 하나뿐이다. 승인은 한 번만 받는다.

## 3. 커밋 실행

`/commit` 5단계의 (1) 스테이징 → (2) 토큰 발급(단독 호출) → (3) `git commit -m … -m …` 을 커밋마다 반복한다.
`.commit-docs-ok` 는 발급할 일이 없다.

영역명이 확실하면 `docs/commit.md` 를 읽지 않는다. 헷갈릴 때만 읽는다.
**Co-Authored-By 등 생성 도구 서명을 붙이지 않는다.**

## 4. 검증과 마무리

```bash
./.claude/skills/commit/verify.sh 2
```

커밋 해시와 제목, 남겨 둔 변경과 그 이유를 보고한다. push 는 하지 않는다.

## 이 스킬을 쓰면 안 되는 때

- 디자인 시스템이 섞였을 때 — 1단계가 잡아 준다.
- 규칙·상수·경로가 바뀌었을 때 — 문서 점검이 필요하다.
- 판단이 서지 않을 때. 느린 쪽이 안전한 쪽이다.
