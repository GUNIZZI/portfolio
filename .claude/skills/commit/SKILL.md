# commit

Kozipsa `/commit` 을 가져왔다. 화면 문서 3종(menu · plan · qa) 대조만 뺐다 — 이 저장소에 없다.

**가벼운 짝이 있다.** 디자인 시스템을 안 건드렸고 문서 점검이 필요 없는 변경은
`/commit-quick` 이 처리한다. 어느 쪽을 쓸지는 **사용자가 호출로 고른다.**

## 0. 전제

- **`/commit` 호출로만 실행된다.** 평문 "커밋해줘"에는 `/commit` 을 호출해 달라고
  **한 줄로 안내만 하고 끝낸다.** 변경 목록이나 메시지 초안을 덧붙이지 않는다.
- `git commit` 은 PreToolUse 훅(`.claude/hooks/guard-commit.py`)이 막고 있다.
  5단계에서 발급하는 1회용 토큰이 있을 때만 통과한다. 훅을 우회하거나 비활성화하지 않는다.
- husky `pre-commit` 이 lint-staged 와 `tsc` 를 돌린다. 실패하면 고치고 다시 커밋한다. `--no-verify` 를 쓰지 않는다.
- `git push` 는 이 스킬의 범위가 아니다.

인자가 주어지면 커밋 범위 힌트로 쓴다 (예: `/commit src/features/hero`).

## 1. 상태 파악 + 자격증명 차단

```bash
./.claude/skills/commit/status.sh
```

- `(변경 없음)` 이면 **"커밋할 변경 없음"으로 즉시 종료**한다.
- `!!` 로 표시된 파일은 **절대 스테이징하지 않는다.** 사용자에게 알리고 `.gitignore` 보완을 제안한다.
- 본문을 읽고 메시지를 쓴다. `--stat` 만 보고 쓰지 않는다.
- **명령을 쪼개 부르지 않는다.** 이 스크립트 하나로 끝낸다.

## 2. 규칙 문서

메시지를 쓰기 전에 `docs/commit.md` 를 읽는다. 영역 표기와 type 7개가 거기 있다.

## 3. 문서 점검

**모든 커밋에서 이 단계를 거친다.** 코드가 바뀌면 그 코드를 설명하던 문서도 같이 본다.
`docs/index.md` 로 주제를 판정하고, 그 문서가 지금도 사실인지 본다.

| 변경 성격                                 | 봐야 할 곳                               | 무엇을 보나                                 |
| ----------------------------------------- | ---------------------------------------- | ------------------------------------------- |
| 규칙·금지사항·네이밍 규약이 바뀜          | 주제 문서의 원칙·금지사항                | 다음에 같은 작업을 할 때 따를 게 달라졌는가 |
| 토큰 이름·개수가 바뀜                     | `docs/theme.md` · `docs/motion.md` 의 표 | 표의 행이 실제 코드와 맞는가                |
| `src/shared/ui/<Name>/` 를 고침           | 같은 폴더의 `<Name>.md`                  | props · 쓰는 법 · 자주 하는 실수            |
| 파일·폴더 구조나 진입점이 옮겨감          | `docs/architecture.md`, 슬라이스 README  | 적힌 경로가 실제와 어긋남                   |
| 실제 코드와 규칙의 어긋남이 줄거나 늘었음 | 주제 문서의 "미정리 항목"                | 적힌 숫자가 지금도 맞는가                   |
| `.claude/` · `CLAUDE.md` 가 바뀜          | `CLAUDE.md` 와 해당 문서                 | 두 곳이 같은 말을 하는가                    |
| 내부 리팩터링, 스타일, 오타               | 없음                                     | 규칙·경로·상수 어느 것도 안 바뀜            |

**`src/style/tokens/` 나 `src/shared/ui/` 를 건드렸으면 `structure-check` 에이전트에 대조를 먼저 맡긴다.**
돌아온 목록을 그대로 넘기지 말고, 이번 커밋에서 실제로 고칠 것만 수정안으로 정리한다.

정리할 내용은 둘 중 하나다. 문서를 말없이 고쳐 커밋에 끼워 넣지 않는다.

- 고칠 게 있으면: 어느 문서의 어느 대목을 어떻게 바꿀지.
- 고칠 게 없으면: **"왜 없는지"의 근거.** 디자인 시스템 변경이면 승인 후 5-(2) 에서 `.git/.commit-docs-ok` 를 발급한다.

문서에 **없는 정책을 새로 써넣지 않는다.**(루트 `CLAUDE.md` `# 규칙`)

## 4. 관심사 분할 — 3단계 판단과 한 번에 승인받는다

한 커밋 = 한 관심사다.

| 축          | 예                                    |
| ----------- | ------------------------------------- |
| type이 다름 | 기능 추가 + 설정 변경 → 2커밋         |
| 영역이 다름 | `홈 > 히어로` + `공통 > 커서` → 2커밋 |
| 목적이 다름 | 버그 수정 + 겸사겸사 리팩터링 → 2커밋 |

분할표와 3단계의 문서 판단을 **하나의 보고로** 내민다. 스테이징 전이다.

```
| # | type | 영역 | 요약 | 대상 파일 |
| --- | --- | --- | --- | --- |
| 1 | feat | 홈 > 히어로 | 타이틀 글자 단위 등장 모션 추가 | src/features/hero/... |

문서: docs/motion.md 의 … (또는 "변경 불필요 — 근거")
```

- 2커밋 이상이거나 문서 판단이 필요하면 여기서 멈추고 **사용자 승인**을 받는다.
- 1커밋이고 문서도 해당 없으면 그대로 진행한다.
- **두 번 멈추지 않는다.**

## 5. 커밋 실행

커밋 하나마다 아래를 반복한다. **각각 별도의 Bash 호출**이어야 한다.
훅은 명령이 실행되기 _전에_ 검사하므로 토큰 발급과 `git commit` 을 `&&` 로 이으면 차단된다.

```bash
# (1) 해당 관심사의 파일만 스테이징 — git add -A / git add . 금지
git add <파일1> <파일2>
git diff --cached --stat
```

```bash
# (2) 1회용 토큰 발급 (5분 TTL) — 반드시 단독 호출
: > "$(git rev-parse --git-dir)/.commit-skill-token"
```

디자인 시스템 변경인데 문서를 함께 스테이징하지 않은 커밋이면, 3단계에서 "문서 변경 불필요"
컨펌을 받은 뒤에만 아래를 함께 발급한다.

```bash
: > "$(git rev-parse --git-dir)/.commit-docs-ok"
```

```bash
# (3) 커밋 — 제목과 본문을 -m 두 번으로 분리
git commit -m "[feat] 홈 > 히어로 - 타이틀 글자 단위 등장 모션 추가" \
           -m "- 글자마다 STAGGER.tight 간격으로 올라오게 해 첫 화면 리듬을 만듦
- 동작 줄이기에서는 최종 상태로 바로 그림"
```

- `[<type>] <영역 > 하위영역> - <요약>`, type 은 7개뿐, 제목 72자 이내, 마침표 없음
- 본문 불릿은 파일 나열이 아니라 **무엇을 왜**
- **Co-Authored-By 등 생성 도구 서명을 붙이지 않는다.**(`docs/commit.md`)

## 6. 검증

```bash
./.claude/skills/commit/verify.sh 2
```

인자는 이번에 만든 커밋 개수다. 기대 출력은 `통과` 두 줄이다. `!!` 가 보이면 그 커밋을 고친다.
훅에 차단당했다면 토큰 발급을 건너뛴 것이다. **훅을 고치지 말고** 5-(2)부터 다시 한다.

## 7. 마무리

커밋 해시와 제목, 남겨 둔 변경이 있으면 그 이유를 보고한다. push 는 하지 않는다.
